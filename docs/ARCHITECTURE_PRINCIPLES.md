# Architectural Principles & Decision Records

**Canonical Reference for Frontend Architecture Decisions**

---

## Core Architectural Principles

### 1. **Convention Over Configuration**

**Principle:** Developers don't choose patterns; they follow standardized ones.

**Implementation:**
- All entity implementations use identical structure
- Naming conventions are strict (not flexible)
- Patterns are enforced by code review
- New entity creation uses templates (copy-paste)

**Example:**
```typescript
// WRONG ❌ - Creative approach
export function useChemicalView() {
  // Custom state management
  // Different return structure
}

// RIGHT ✅ - Convention followed
export function useChemicalsView() {
  // Standard hooks pattern
  // Predictable return structure
  return {
    filteredItems: [],
    filters: {},
    form: {},
    mutations: {},
    // ... standard shape
  };
}
```

### 2. **Type-Driven Architecture**

**Principle:** Types define contracts. Implementation follows naturally.

**Implementation:**
- Start with `*Api` (backend response)
- Define `*Payload` (what we send)
- Everything else derives from these
- Form types are generated by convention

**Example:**
```typescript
// Types define the contract
export interface ChemicalApi {
  id: number;
  common_name: string;
  category: ChemicalCategory;
  quantity: number;
  // ...
}

export interface ChemicalPayload {
  common_name: string;
  category: ChemicalCategory;
  quantity: number;
  // ... matches Api (minus ID/timestamps)
}

// Form type is derived
export interface ChemicalForm {
  name: string;              // ← mapped from common_name
  category: string;
  quantity: string;          // ← string for form inputs
  // ... all fields strings or null
}
```

### 3. **Hook-Based Composition**

**Principle:** All stateful logic lives in hooks. Components are pure.

**Implementation:**
- Page components render only
- View hooks contain all logic
- Detail hooks manage sections
- Form hooks handle submission

**Example:**
```typescript
// Page: Pure composition (20 lines)
const Chemicals = () => {
  const view = useChemicalsView();
  
  return (
    <ListPage>
      <GridTableRenderer
        items={view.filteredItems}
        viewMode={view.viewMode}
        // ... props
      />
    </ListPage>
  );
};

// Hook: All logic (200 lines)
const useChemicalsView = () => {
  // State, queries, mutations, dialogs, etc.
  return { /* standard shape */ };
};
```

### 4. **Progressive Disclosure**

**Principle:** Basic features are simple. Advanced features opt-in.

**Implementation:**
- Minimal entity needs <500 lines
- Advanced features are extensions
- Equipment's borrow/return is extraActions
- Detail sections are configurable

**Example:**
```typescript
// Basic entity: Pure CRUD
const entity = createEntityService(name, endpoint);

// Advanced entity: With special workflow
const entity = createEntityService(name, endpoint);
const borrowMutation = useBorrowEquipment(); // ← opt-in
```

### 5. **Explicit Over Implicit**

**Principle:** Code should be obvious, not clever.

**Implementation:**
- No magic or implicit conversions
- Field mapping is explicit (FIELD_MAP)
- Error messages are specific
- Assumptions are documented

**Example:**
```typescript
// IMPLICIT ❌ - What's happening?
const form = transformApiToForm(api);

// EXPLICIT ✅ - Clear intent
const form: ChemicalForm = {
  name: api.common_name,
  chemicalCode: api.chemical_code ?? "",
  category: api.category,
  // ... all fields explicit
};
```

### 6. **Single Responsibility**

**Principle:** Each module has one reason to change.

**Implementation:**
- Services: Data fetching only
- Hooks: State management
- Components: Rendering only
- Types: Data shape only

**Example:**
```typescript
// chemicalService.ts - ONLY data fetching
export const useChemicalList = entity.useList;
export const useChemicalById = entity.useById;

// useChemicalsView.ts - ONLY state management
const view = useChemicalsView();
// return { filters, form, mutations, ... }

// Chemicals.tsx - ONLY rendering
<GridTableRenderer items={view.filteredItems} />
```

### 7. **DRY (Don't Repeat Yourself) - When Justified**

**Principle:** Extract duplication when it appears in 2+ places. Not before.

**Implementation:**
- useEntityForm: Used by all 6 entities → extract
- Image upload: Used by all 6 forms → extract
- Product card footer: Used consistently → extract
- Detail section renderer: Used in detail pages → extract

**Anti-Pattern:**
```typescript
// DON'T extract after 1 usage
// Wait until 2-3 entities use same pattern
// This avoids over-abstraction

// DO extract when pattern appears 2+ times
// Image upload: Chemical, Equipment, Species, etc. → extract
```

## Architectural Decision Records (ADRs)

### ADR-001: Factory Pattern for Services

**Status:** ✅ ACCEPTED

**Context:**
All entity services need identical structure: list, byId, create, update, delete queries/mutations.

**Decision:**
Use `createEntityService<TApi, TPayload>()` factory. All services are 14-line wrappers.

**Rationale:**
- Zero code duplication across 6 entities
- Consistent query cache strategy
- Behavior is predictable
- New service takes 2 minutes

**Consequence:**
- Service logic lives in factory, not per-entity
- Cannot customize service behavior (by design)
- Query keys are always hierarchical

**Example:**
```typescript
// chemicalService.ts
const entity = createEntityService<ChemicalApi, ChemicalPayload>(
  "chemicals",
  "/chemicals"
);
export const useChemicalList = entity.useList;
export const useCreateChemical = entity.useCreate;
// ... etc
```

### ADR-002: Three-Tier Type System

**Status:** ✅ ACCEPTED

**Context:**
Need clear separation between backend responses, payloads we send, and form state.

**Decision:**
Define three types per entity: `*Api`, `*Payload`, `*Form`. Each serves one purpose.

**Rationale:**
- Backend changes don't propagate to UI
- Form library changes don't affect types
- Field mapping is explicit
- Type safety throughout

**Consequence:**
- New entity requires 3 type definitions (vs. 1 generic)
- Conversions must be explicit
- Field mapping becomes necessary

**Example:**
```typescript
// Tier 1: Backend response
interface ChemicalApi {
  id: number;
  common_name: string;
  created_at: string;
}

// Tier 2: What we send
interface ChemicalPayload {
  common_name: string;
  // No ID or timestamps
}

// Tier 3: Form state
interface ChemicalForm {
  name: string;  // ← camelCase for form
  // All strings for inputs
}
```

### ADR-003: View Hook as Single State Container

**Status:** ✅ ACCEPTED

**Context:**
Page state can be split across multiple hooks (filters, form, mutations) or consolidated.

**Decision:**
All page-level state lives in one `useXxxView()` hook per entity.

**Rationale:**
- Single source of truth
- Predictable hook structure
- Easy to understand page behavior
- Testable in isolation

**Consequence:**
- View hook can be 200+ lines
- Cannot reuse form logic across pages
- Requires strict structure

**Alternative Considered:**
Multiple hooks per page (useFilters, useForm, useMutations)
- ❌ Reduces predictability
- ❌ Harder to understand page flow

### ADR-004: ProductCard as Standard Card Component

**Status:** ✅ ACCEPTED

**Context:**
All entities display items in grid/card format. Need consistent card UI.

**Decision:**
Use unified `<ProductCard>` component for all entities. Delete via `onDelete` prop.

**Rationale:**
- Consistent UX across entities
- Easier to update styling everywhere
- Standard delete button location
- Extensible via props

**Consequence:**
- Cannot customize card layout per entity
- Actions are limited to Edit/Delete (extensible via footer)
- Equipment's borrow/return is extraAction

**Example:**
```typescript
<ProductCard
  title={item.name}
  image={item.image}
  onEdit={() => edit(item)}
  onDelete={() => delete(item)}
  extraActions={<BorrowButton />}  // Equipment-specific
/>
```

### ADR-005: Hierarchical Query Cache Keys

**Status:** ✅ ACCEPTED

**Context:**
React Query uses cache keys to deduplicate requests and invalidate data.

**Decision:**
Use hierarchical structure: `[entity, type, params]`

**Rationale:**
- Efficient invalidation (all lists, specific detail, etc.)
- No over-fetching on mutations
- Predictable cache behavior
- Easy to debug

**Consequence:**
- Cache keys must follow pattern
- Query functions must use factory
- Cannot customize key structure

**Example:**
```typescript
const keys = {
  all: ["chemicals"],
  lists: () => ["chemicals", "list"],
  list: (params) => ["chemicals", "list", params],
  detail: (id) => ["chemicals", "detail", id],
};

// Invalidation
queryClient.invalidateQueries({ queryKey: keys.all }); // Everything
queryClient.invalidateQueries({ queryKey: keys.lists() }); // All lists
queryClient.invalidateQueries({ queryKey: keys.detail(5) }); // Specific item
```

### ADR-006: Field Mapping for Validation Errors

**Status:** ✅ ACCEPTED

**Context:**
Backend field names are snake_case. Frontend form fields are camelCase.

**Decision:**
Explicit `FIELD_MAP` dictionary in each view hook. Maps backend → form field.

**Rationale:**
- Validation errors automatically mapped
- No magic or implicit conversions
- Easy to debug field mismatches
- Type-safe

**Consequence:**
- Must maintain field map in each view hook
- Map must be complete and accurate
- Unmapped fields won't have error messages

**Example:**
```typescript
const CHEMICAL_FIELD_MAP: Record<string, keyof ChemicalForm> = {
  common_name: "name",
  chemical_code: "chemicalCode",
  storage_location: "storageLocation",
  // ... etc - must be complete
};

// Backend error: { common_name: ["Name is required"] }
// Mapped to form: { name: "Name is required" }
```

### ADR-007: Delete Confirmation Pattern

**Status:** ✅ ACCEPTED

**Context:**
Destructive action (delete) should have confirmation. Need consistent pattern.

**Decision:**
Two-phase delete: `requestDelete()` → `confirmDelete()` with dialog in between.

**Rationale:**
- User cannot delete by accident
- Clear confirmation message
- Consistent across entities
- Easily testable

**Consequence:**
- All deletes must use `useConfirmDialog()`
- Cannot delete without confirmation
- Delete button calls `requestDelete()`, not `delete()`

**Example:**
```typescript
// Phase 1: User clicks delete
const requestDeleteChemical = (item) => {
  deleteDialog.requestConfirm(String(item.id), {
    title: `Delete ${item.common_name}?`,
    description: "This cannot be undone.",
  });
};

// Phase 2: Dialog appears, user confirms
const confirmDeleteChemical = () => {
  deleteDialog.confirm((id) => {
    deleteMutation.mutate(Number(id));
  });
};
```

### ADR-008: Image Upload as Optional Feature

**Status:** ✅ ACCEPTED

**Context:**
Most entities support images, but not all. Need flexible pattern.

**Decision:**
Image upload is optional in form. If `image` field in Payload, form supports it.

**Rationale:**
- No forced pattern on all entities
- Natural extension point
- Consistent image handling
- Easy to test

**Consequence:**
- Not all entities support images
- Image upload requires `useImageUpload()` hook
- Backend must support multipart form data

### ADR-009: Detail Pages as Section Registry

**Status:** ✅ ACCEPTED

**Context:**
Detail pages have different sections per entity (Overview, Details, History, etc.).

**Decision:**
Sections are configuration. Renderer is generic. Domain functions extract data.

**Rationale:**
- Easy to add/remove sections
- Consistent detail page structure
- Sections are independently testable
- Easy to conditionally show sections

**Consequence:**
- Must define section config
- Sections receive same data format
- No custom layouts possible

**Example:**
```typescript
const SECTIONS: DetailSection[] = [
  {
    id: "overview",
    title: "Overview",
    component: OverviewSection,
    visible: (data) => true,
    order: 1,
  },
  {
    id: "details",
    title: "Details",
    component: DetailsSection,
    visible: (data) => data.expanded,  // Conditional
    order: 2,
  },
];
```

### ADR-010: No Page-Level State in Components

**Status:** ✅ ACCEPTED

**Context:**
Page components can have local state (form, filters, etc.) or use hooks.

**Decision:**
ALL page-level state must live in hooks. Never use `useState` in page components.

**Rationale:**
- Logic is reusable
- Components remain pure
- Testing is simpler
- Server components compatible
- Easy to debug

**Consequence:**
- Page components are 100% pure
- Logic lives in hooks
- Cannot use component state for temporary values

**Anti-Pattern:**
```typescript
// ❌ DON'T DO THIS
const Chemicals = () => {
  const [filters, setFilters] = useState({});  // ← Page state in component
  
  return <div>{/* ... */}</div>;
};

// ✅ DO THIS
const Chemicals = () => {
  const view = useChemicalsView();  // ← All state in hook
  
  return <div>{/* ... */}</div>;
};
```

## Key Conventions

### Naming Conventions

**Hooks:** `use{Entity}{Feature}`
```typescript
useChemicalsView()      // Page state
useChemicalDetail()     // Detail page state
useChemicalForm()       // Form state (generic)
```

**Components:** `{Entity}{Feature}`
```typescript
<ChemicalGrid />
<ChemicalFormDialog />
<ChemicalDetailRenderer />
```

**Services:** `{entity}Service`
```typescript
chemicalService
equipmentService
plantSpeciesService
```

**Types:** `{Entity}{Type}`
```typescript
ChemicalApi
ChemicalPayload
ChemicalForm
ChemicalItem  // Api + enriched fields (icon, color)
```

**Constants:** `UPPER_SNAKE_CASE`
```typescript
EMPTY_CHEMICAL
CHEMICAL_FIELD_MAP
CHEMICAL_CATEGORIES
```

## Validation & Error Handling

### Form Validation Pattern

```typescript
// Step 1: Client validation (optional)
function validateChemicalForm(form: ChemicalForm): Errors {
  const errors: Errors = {};
  if (!form.name) errors.name = "Name is required";
  if (!form.quantity) errors.quantity = "Quantity is required";
  return errors;
}

// Step 2: Server validation
try {
  await createMutation.mutateAsync(payload);
} catch (err) {
  if (isValidationError(err)) {
    // Backend errors: { common_name: ["Name is required"] }
    // Mapped via FIELD_MAP: { name: "Name is required" }
    form.setBackendErrors(err.response.data.errors);
  }
  toast.error("Failed to save");
}

// Step 3: Display errors in form
<input
  value={form.form.name}
  onChange={(e) => form.updateField("name", e.target.value)}
  className={form.errors.name ? "border-destructive" : ""}
/>
{form.errors.name && <span className="text-destructive">{form.errors.name}</span>}
```

## Query & Mutation Pattern

### Standard Query Pattern

```typescript
// List queries with parameters
const { data, isLoading, isError } = useChemicalList({
  page: 1,
  search: "aspirin",
  status: "active",
});

// Specific item queries
const { data: chemical } = useChemicalById(5);

// Queries automatically use hierarchical cache
// No manual cache invalidation needed
```

### Standard Mutation Pattern

```typescript
// Create/Update/Delete mutations
const createMutation = useCreateChemical();

createMutation.mutate(payload, {
  onSuccess: () => {
    toast.success("Created");
    // Cache auto-invalidated by factory
  },
  onError: (err) => {
    handleError(err);
  },
});

// Never manually invalidate queries
// Factory handles it for all entities
```

## Performance Considerations

### Query Caching

**Automatic:** Factory invalidates root key on any mutation
```typescript
// User creates chemical
// All chemical queries re-fetch
// (This is intentional - simple, predictable)
```

**Could optimize:**
```typescript
// Instead of invalidating all
queryClient.invalidateQueries({ queryKey: keys.all });

// Could invalidate only affected queries
queryClient.setQueryData(keys.detail(id), newItem);
queryClient.invalidateQueries({ queryKey: keys.lists() });
```

**Decision:** Keep it simple. If performance becomes issue, optimize then.
